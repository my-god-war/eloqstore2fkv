# ประสิทธิภาพ

ดาวน์โหลด `perf-latest` ของ `fkv_bench` จากที่เก็บ fkv และรันปริมาณงานเดียวกันบนเครื่องแบบคงที่
และเปรียบเทียบปริมาณงาน ควอนไทล์เวลาในการตอบสนอง และ RSS สูงสุดกับค่าพื้นฐาน C++

แหล่งพารามิเตอร์สอดคล้องกับ fkv:

- `PERF_ROWS`
- `PERF_BATCH_SIZE`
- `PERF_WORKLOAD`
- `PERF_BENCH_ROOT`

บรรทัดฐาน C++ รันโดยสภาพแวดล้อมของ oracle `simple_bench` จากนั้นส่งออกตามสคีมาเดียวกันและเผยแพร่ไปยัง
`perf-baseline` ปล่อยเนื้อหา ผลการเปรียบเทียบจะถูกเขียนกลับไปยังเอกสารคลังสินค้า และไซต์จะแสดงผล Markdown โดยตรง
ไม่มีการรักษาชั้นข้อมูล JSON

การเขียน 1 ล้านรายการ (10,000 ชุด) สอดคล้องกับ
`io_write_at_num=48,625`, `io_data_sync_num=10,000` นั่นคือข้อมูลจะถูกซิงโครไนซ์หนึ่งครั้งต่อแบตช์
เมตริกเพิ่มเติมสนิม: สแกน `141,166 kv/s`, Fullscan `108,274 kv/s`, การขยายการเขียน `2.57x`
(`proc_io_write` 329 MB / 128 MB การเขียนแบบลอจิคัล), `4.86` เขียนการเรียกของระบบต่อแบตช์
อัตราส่วนพื้นที่จัดเก็บข้อมูลคำนวณจาก 1M × 128B = ข้อมูลที่ระบุ 128 MB C ++ ไม่ทริกเกอร์ GC/compact ในครั้งนี้
จึงมีหน้าประวัติศาสตร์เพิ่มมากขึ้น ไม่ใช่หมายเลขความสามารถเดียวกันกับ "การขยายพื้นที่ข้อมูลการอยู่รอด"
เวลาแฝงหาง P99.9 ของ Rust ยังคงแย่กว่า C ++ (ใส่ 223.3 ms เทียบกับ 86.0 ms รับ 355.5 ms เทียบกับ
48.2 มิลลิวินาที) เส้นฐานเดียวมีความผันผวนอย่างมาก โปรดดูรายละเอียดในรายงานประสิทธิภาพภายใน

**หมายเหตุ**: `write-read` ของ C++ หมายความว่าเธรดการเขียนและเธรดการอ่านทำงานพร้อมกัน และปัจจุบันเป็นสนิม
“เขียนให้จบ เปิดใหม่ แล้วอ่านใหม่” ไม่มีการแข่งขันเขียนในเวทีการอ่าน ดังนั้นตัวคูณของ `write-read` จึงไม่สามารถถือเป็นได้
การอ่านล้วนๆ / การเขียนล้วนๆ การเปรียบเทียบที่เข้มงวดควรเห็น `scripts/perf_local.sh --symmetric`
ผลลัพธ์สองคู่จะถูกส่งออก: เขียนอย่างเดียวและอ่านอย่างเดียว หมายเลขนักวิ่งร่วมเดี่ยวใช้สำหรับการถดถอยเท่านั้น
แนวโน้ม การเผยแพร่จะถูกตัดสินโดยใช้ค่ามัธยฐานของ `--runs`
