# 冷抽检报告 2026-11-05（dragon，独立第三路）

## 方法与口径

对 `issue/reviewed/` 已归档条目做**独立冷抽检**：**不读条目自己的复审小节结论**，只按它声称的
「代码守卫」或「测试 / 注入点」去**今日盘面**找证据，判断归档结论是否随着近期的大面积重构
（当晚跨 `fkv_page` / `fkv_large` / `fkv_btree` / `fkv_store` / `fkv_task_read` /
`fkv_task_write` / `fkv_runtime` / `fkv_cloud` / `fkv_shard` / `fkv_io_compio` 的连续改动）
发生回退（rot）。

- 样本：11 项，覆盖 4 个 crate（`fkv_io_compio` / `fkv_mapping` / `fkv_shard` /
  `fkv_task_gc` / `fkv_runtime` / `fkv_page` / `fkv_manifest`）。
- 检查分两类：**代码守卫**（条件 / 次序 / 数据结构形状）8 项，**证据侧**（用例与
  failpoint 是否还在）3 项。
- 取证方式：`rg` 定位当前行号 + 逐行读语义，不依赖条目里的旧行号。

## 覆盖边界（如实记录，避免高估）

- 样本 11 项 / `reviewed` 目录 288 份，**抽样率约 4%**，不是全量复核。
- 抽的是「守卫与证据是否还在」，**不是**重新论证结论本身是否正确（那是原审查的职责）。
- 未覆盖：`reviewed/` 里 `00-*` 主题报告（11 份叙事汇总）、以及 7 份 `done/` 待复审条目
  （后者由对方的 PASS 流程负责）。

## 建议的后续用法

1. 每次跨 crate 大重构后，按同一方法抽 10 项左右（优先挑「守卫类」与「failpoint 类」）；
2. 若某轮抽到 rot：把该条从 `reviewed/` 拉回 `todo/` 并附新证据（现行流程即可承接）；
3. 抽检不必等重构结束，但**必须在 `./test.sh` 双门禁绿之后**做，否则无法区分
   「结论烂了」与「仓库正在改」。
